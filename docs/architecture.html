Architecture & data model

How a two-tap check-in becomes today's menu — and where the boundaries fall: what runs on the phone, what crosses the network, what holds a secret, and what the paywall actually cuts through.

Five diagrams. The first is the whole system; the rest zoom into the three decisions that were hard to get right — the data model, the promise that the screen never blocks, and the two boundaries (a secret, and a paywall) that constrain everything around them.

01The system

Everything that decides anything runs on the phone. PlanEngine is a pure function of profile, check-in, and history — no network, no I/O, no framework. That single choice is what lets the menu appear instantly, work on a plane, and be exhaustively unit-tested.

Three things sit across the network, and each is there for a different reason: YouTube because that is where Simone's classes live, RevenueCat because purchases must be verified somewhere we control, and a Cloudflare Worker because an API key inside an iOS binary is a published API key.

02The data model

Eight SwiftData entities, split down one line: things about her (profile, check-ins, plans, logs — all local, never transmitted) and the catalog (sessions, shipped as versioned JSON and seeded on first launch). The catalog is read-only to the app, which is what makes replacing it a data drop rather than a migration.

Profile is a singleton — there are no accounts, so there is exactly one. Affinity is the quiet one: it accumulates from how sessions actually felt and feeds back into scoring, so the engine gets better without ever asking her a question about it.

ExerciseTerm is the movement glossary — public-domain instructions for the moves an authored session names. It is reachable only from a step inside a session she is already doing, never as a browsable list, which is why it hangs off Session rather than sitting beside it.

03Why the screen never waits

The engine is synchronous and local, so the menu is on screen before the network has been touched. The written line arrives afterward, or it doesn't. Both are fine, and only one of them is visible.

04The first boundary: a secret

An .ipa is a zip file. A key inside it — in source, in a plist, in the keychain, obfuscated, it makes no difference — is a published key. So the key lives in a Worker and the app never holds it.

Once that hop exists it earns its keep twice over: the Worker asks RevenueCat whether this install is actually pro before spending a token, so free installs cannot reach the model at all. Cost scales with subscribers, not downloads.

05The second boundary: the paywall

YouTube's developer policies are unambiguous: you cannot charge a fee for content that YouTube offers free. Simone's classes therefore can never sit behind the Pro wall — not one of them.

That reads like a constraint on the business model and is actually a description of it. The paywall doesn't run between free content and paid content; it runs between content and the decision about which content. YouTube has her entire library and no opinion about which class matters this morning. The opinion is the product.

06Module map

Every external dependency sits behind a protocol with a fake implementation, so the whole app runs in tests and SwiftUI previews with no network and no store account.

Two things are deliberately absent. There is no analytics SDK collecting health data and no backend holding user records — the profile, the check-ins, and the logs never leave the phone.
